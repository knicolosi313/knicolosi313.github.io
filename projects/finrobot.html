What it does

This is the explanation I use when demoing it, because it's the one that actually lands with people who don't write software:

You type in a stock ticker. One bot goes out and gathers the research. It hands that to the main bot, which decides what's needed and passes the work along: to a graph maker that draws the charts, and to a final bot that formats everything into a clean document. What comes back is a PDF you could actually hand to someone.

Three phases, each handled by something specialised. That framing survives contact with a non-technical audience, and it also happens to be an accurate description of the architecture rather than a simplification of it.

Why MCP, and not just API calls

The honest answer to "why not call the APIs directly in Python" is that we could have; for a single-model pipeline it would have been less code. The reason MCP earns its place here is that this isn't a single-model pipeline.

Research, charting, and formatting are genuinely different problems, and the best tool for each is different. The Model Context Protocol lets each one run as its own server, exposing its capabilities through a consistent interface, so the orchestrator can call them without knowing or caring what's behind them. Swapping the model inside one server doesn't touch the other two. 

mcp_servers:
  - name: "research"           # Perplexity: search-native retrieval
  - name: "chart_generation"   # Matplotlib: deterministic, no model
  - name: "formatting"         # Claude: document layout & styling

orchestrator: Gemini           # tool calling and coordination

Model routing by task

  • Perplexity for research. It's search-native, built to retrieve and cite current information. Asking a general-purpose model to recall market data from training weights is the wrong shape of question entirely.
  • Gemini as orchestrator. It holds the conversation, decides which tools to invoke, and sequences the phases.
  • Claude for formatting. Turning a pile of research and charts into well-structured HTML that survives conversion to PDF is a writing-and-layout problem, and that's where it's strongest. This server originally ran on Gemini (the old implementation is still in the tree as gemini_old/), and moving it was a straight quality decision.
  • Matplotlib for charts, deliberately not a model. Charts have exactly one correct answer given the data. A deterministic library gets it right every time for free; an LLM would be slower, cost money, and occasionally invent a data point. The interesting judgment in an AI project is often knowing which parts shouldn't be AI.

The trade-off

Three servers and three providers means three sets of credentials, three failure modes, and a process-management story that a single script wouldn't have. In exchange each phase is independently swappable and testable, and we could replace the formatting model without regression risk to research. For a project whose stated purpose is learning how agent architectures fit together, that's the right side of the trade.

Things that only show up when you run it

Rate limits are an architecture problem

The orchestrator sits in the middle of every request, which makes it the first thing to hit a rate limit. Gemini returning HTTP 429 mid-pipeline doesn't just fail one call; it strands a report halfway through, after the research phase has already been paid for.

Sends now retry with exponential backoff: five attempts, starting at two seconds and doubling. It's a small piece of code that turns a class of hard failure into a slow success, and it only became obviously necessary once several people were demoing simultaneously.

PDF conversion is its own problem

Getting a report to look right in a browser is not the same as getting it to look right on a page. Export runs through Playwright, driving a real browser engine to render the HTML and print it, because that's the only reliable way to get output that matches what you saw on screen.

Presenting it

FinRobot was presented at ImagineRIT 2026 to roughly 200–300 attendees across the day, alongside demos at club meetings and tabling events.

The audience at ImagineRIT is deliberately general: students, faculty, industry visitors, and members of the public with no technical background. Explaining a multi-agent MCP pipeline to someone who has never heard of any of those words is a genuinely useful constraint, and it's where the "one bot gathers, one draws, one writes" framing came from. Being forced to describe a system without jargon is a fast way to find out which parts of your own design you don't actually understand.

Where it's going

FinRobot started as an exploration project, a way for the AI Club to learn how agent architectures, MCP, and multi-model pipelines actually behave when you build something real with them. That's still its primary purpose.

The current direction is evolving it toward a practical use case for investors: output someone would genuinely use for research rather than a demonstration that it can be produced. It won't be commercialised. It's a club project, built by club members for learning, and it stays that way.

Six people have contributed to it so far. My work has centred on the MCP tooling and the server-side logic behind it, the layer that has to turn inconsistent, rate-limited, occasionally-disagreeing external sources into something predictable enough for a model to reason over.
